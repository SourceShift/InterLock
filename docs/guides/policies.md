# Declarative policies

Write rules as data, in JSON (or YAML, if PyYAML is installed), instead of
Python. A policy file can be reviewed by someone who doesn't write Python,
changed without a deploy, checked before it ships, and reloaded while the
guard runs.

```json
{
  "version": 1,
  "rules": [
    {"id": "no-force-push", "verdict": "block",
     "reason": "force-push to a default branch",
     "when": {"intent": "git.push.force:default"}},
    {"id": "cap-rows", "verdict": "modify", "set": {"limit": 100},
     "reason": "row limit capped",
     "when": {"all": [{"action": "query_db"}, {"arg": "limit", "gt": 100}]}},
    {"id": "big-payments", "verdict": "escalate",
     "reason": "payments over 1,000 need a human",
     "when": {"all": [{"action": {"glob": "pay_*"}}, {"arg": "amount", "gt": 1000}]}},
    {"id": "egress", "detector": "data_egress.network_egress_guard",
     "with": {"allowed_hosts": ["api.acme.com"]}, "widenable": ["allowed_hosts"]}
  ]
}
```

```python
import interlock
from interlock.policy.declarative import load_policy_file

interlock.install(engine=load_policy_file("policy.json", watch=2.0))
```

`watch=2.0` re-checks the file at most every two seconds and reloads it when it
changes. A file that no longer parses leaves the last good policy running and
logs the error (`engine.last_error` says why). Rules added in code with
`engine.add_rule(...)` are part of the running policy: a successful reload
re-appends them after the freshly loaded rules, and a failed reload leaves the
rule set exactly as it was.

## Rules

| Key | Meaning |
|---|---|
| `id` | Required, unique. Becomes the `policy_id` on decisions and receipts |
| `verdict` | `block`, `escalate` (ask a human; see [approvals](approvals.md)) or `modify` |
| `when` | The condition (below) |
| `reason` | What a blocked caller or an approver is told |
| `set` | For `modify`: the argument values to rewrite |
| `phase` | `call` (default) or `result` |
| `on` | Limit the rule to an action, a list of actions, or `{"glob": ...}` |
| `locked` | `true`: no file that extends this one, and no overlay, can disable it |
| `detector` + `with` | Instead of `when`/`verdict`: any [catalogued detector](../reference/detectors.md), by name, with its keyword arguments |
| `widenable` | For a detector rule: the list parameters an overlay may extend |

There is no `allow` verdict. The engine allows by default, and a block from any
rule always wins.

## Learning a baseline from receipts

`interlock learn` drafts a policy from what your guard actually allowed, so a
deployment starts from observed behaviour instead of a blank page:

```bash
interlock learn --receipts audit.jsonl --out baseline.json
interlock policy check baseline.json        # review it, then install it
```

It reads a receipt log (the NDJSON a `FileSink` writes), keeps every action
observed with an `ALLOW` verdict, and emits a policy with a single rule:

```json
{
  "version": 1,
  "name": "learned-behavioural-baseline",
  "description": "generated by interlock learn from 4 allowed receipt(s); review before installing",
  "rules": [
    {"id": "learn-escalate-unseen", "verdict": "escalate",
     "reason": "outside the observed envelope: a human decides before this runs",
     "description": "observed actions (receipt count): read_file=1, search_web=3",
     "when": {"not": {"action": ["read_file", "search_web"]}}}
  ]
}
```

Because there is no `allow` verdict, "allow what we saw" is one *complement*
rule: escalate when the action is **not** in the observed set. Observed actions
fall through to the engine's default allow; anything else is escalated to a
human. The counted evidence rides in the `description` field (the rule and
document key sets are closed, so there is nowhere else to put it).

A receipt whose verdict was `block`, `escalate` or `modify` never enters the
envelope — a refused action must not become "observed and fine". Those
receipts, and any `receipts.dropped` audit artifact, are counted and reported
instead.

The draft is **never auto-enforced**: `learn` writes the file you name and
nothing else. It installs nothing, enables nothing, locks nothing and emits no
`block` rule, so the worst a careless install can do is ask a human about the
unseen. The output is deterministic — sorted actions, fixed rule id, no
timestamps — so two runs over the same log are byte-identical and the diff
between two drafts is worth reviewing.

Exit codes: `0` wrote the policy; `3` the log could not be read or held no
`ALLOW` receipt, or the output could not be written (no file is written in
those cases); `64` the command line was wrong.

## Conditions

| Condition | Matches when |
|---|---|
| `{"all": [c, ...]}` / `{"any": [...]}` / `{"not": c}` | all / any / none of the parts match |
| `{"action": "name"}`, `["a", "b"]`, `{"glob": "mcp__github__*"}` | the tool name matches |
| `{"field": F, OP: value}` | an event field passes the test; F is `action`, `principal`, `phase`, `span_id`, `parent_principal` or `call_id` |
| `{"arg": "name", OP: value}` | a tool argument passes the test; `"a.b"` reaches into nested objects, `"items.0"` into lists |
| `{"intent": "selector"}` | a string argument is a shell command that does this (add `"arg": "command"` to look at one argument only) |
| `{"a2a": "selector"}` | an agent-to-agent call's peer or card matches; `"peer"` / `"peer:<glob>"` reads the `"peer"` argument, `"card"` / `"card.<field>[:<glob>]"` reads the `"card"` argument (add `"arg": "peer"` to read the peer from one argument) |
| `{"flow": {"source": s, "sink": t}}` | an argument at `t` carries a value that entered from `s`; labels are `tool:<action>` and `principal:<id>`, and both sides accept globs |

| Operator | Test |
|---|---|
| `eq`, `ne` | equal / not equal (a missing argument is `ne` anything) |
| `in`, `not_in` | in / not in a list |
| `gt`, `ge`, `lt`, `le` | numeric comparison (strings and booleans never match) |
| `contains` | substring of a string, or member of a list |
| `startswith`, `endswith` | string prefix / suffix |
| `glob` | shell-style pattern, whole string |
| `matches` | regular expression (at most 512 characters; scans the first 64 KiB) |
| `exists` | `true`: the argument is present and not null |

Shell-intent selectors are listed in [parsed shell commands](detectors.md#parsed-shell-commands):
`git.push.force`, `pkg.publish`, `net.fetch_exec`, `fs.delete.recursive:critical`
and so on. A prefix matches its family (`"git"` covers every `git.*` intent),
and `:detail` or `:critical` narrows it.

## Provenance: source to sink

A flat `arg` condition judges the text; it cannot tell a URL the user typed
from a URL copied out of a fetched page. A `flow` condition does:

```json
{"id": "no-fetched-email", "verdict": "block",
 "reason": "a fetched page reached an email field",
 "when": {"flow": {"source": "tool:fetch_url", "sink": "body"}}}
```

The boundary records what a guarded tool returned under `tool:<action>` and
`principal:<id>`, and puts those labels on the per-argument `event.origins` map
when a later call carries the same text. `source` matches an origin label,
`sink` matches an argument path; both accept a list and shell-style globs
(`tool:*`, `principal:acme/*`, `payload.*`). A top-level sink also matches that
field one level down, so `body` sees `payload.body`. The verdict's
`attributed_to` is the argument that carried the tainted value.

The scope is honest: provenance is tracked at the boundary by matching text, so
a value rewritten by a string operation (`value[::-1]`, a paraphrase, a
re-encoding) loses its origin. It catches the common exfiltration shape — a
document, a row, or a secret copied verbatim into an outbound field — not an
adversary who transforms it on the way. The tracker is bounded; see
[`FlowTracker`](../reference/python-api.md#flowtracker).

The `network_egress_guard` detector can apply the same check to every egress
action: `{"detector": "data_egress.network_egress_guard", "with":
{"allowed_hosts": ["api.acme.com"], "block_origins": ["tool:fetch_url"]}}`
denies a payload carrying fetched data even to an allowlisted host.

## Mistakes fail at load, not in production

A rule that loads cleanly but can never fire is the worst kind. So:

- An unknown key, field or operator is an error that names the valid choices and
  the likely one you meant (`'equals'` → `eq`, `'principle'` → `principal`).
- For actions with a known argument schema, a misspelled argument is an error
  too: `{"on": "Bash", "when": {"arg": "cmd", ...}}` reports
  "Bash has no argument 'cmd' (did you mean 'command'?)". The coding-agent tools
  are known out of the box; declare your own with a `"tools"` section:
  `"tools": {"query_db": ["sql", "limit"]}`.
- An invalid rule is **quarantined**: skipped, logged, and listed in
  `engine.quarantined` with the reason. The rest of the file still loads.

```bash
interlock policy check policy.json
```

prints the rules, the locked ones and anything quarantined, and exits 1 if any
rule was skipped, so you can run it in CI.

## Building on another policy

```json
{"version": 1, "extends": "builtin:coding-agent", "disable": ["privilege"],
 "rules": [...]}
```

`extends` takes a built-in pack (`builtin:coding-agent`) or a path relative to
this file. `disable` removes inherited rules by id. A `locked` rule can't be
disabled; the attempt is listed in `quarantined` and the rule stays.

## Project overlays

An overlay is a policy file a project carries (`.interlock/policy.json`, found
by walking up from the working directory to the git root). It's written by
whoever controls the repository, which may be the agent itself. So:

- **It is ignored until a human trusts it**, by content hash:
  `interlock trust add`. Editing the file revokes trust until it's re-approved.
- **It can only tighten.** An overlay may add rules that `block` or `escalate`,
  and extend lists that the base marks `widenable`:

  ```json
  {"widen": {"egress": {"allowed_hosts": ["staging.acme.com"]}},
   "rules": [{"id": "no-prod-env", "verdict": "block",
              "when": {"arg": "env", "eq": "prod"}}]}
  ```

  It can't add a `modify` rule, a rule with `"set"`, or any detector rule: a
  rewrite runs before the rules it would otherwise have to pass, so an overlay
  could rewrite the very argument a locked rule inspects. It also can't
  `disable` anything, replace a base rule's id, lock a rule, or widen a list the
  base didn't mark widenable. An overlay that tries is ignored whole.
- **Its `tools` entries are local.** An overlay may declare a new action so its
  own rules' argument names type-check, but it may not redefine an action the
  base declares with a different argument list, and no schema it registers
  outlives the load: the next `load_policy` sees exactly the map it saw before.

```python
from interlock.policy.declarative import load_policy_file
from interlock.policy.trust import TrustStore, find_overlay

overlay = find_overlay(".")
engine = load_policy_file("policy.json", overlays=[overlay] if overlay else [],
                          trust=TrustStore())
```

Applied and ignored overlays are recorded as `policy.overlay` receipts.
`engine.overlays` lists each one with its status. The trust file
(`~/.interlock/trusted.json`) must be somewhere the agent can't write.

## The policy epoch

`engine.epoch` is a hash of the effective policy documents. It is stable across
processes for the same files, it changes when they change, and it's stamped on
every receipt. Approvals are bound to it, so a policy change invalidates them.

## Native evaluation (opt-in)

When the optional [`rust/`](https://github.com/SourceShift/InterLock/blob/main/rust/README.md)
module is installed and `INTERLOCK_NATIVE=1` is set, a policy that the native
planner can express **in full** is evaluated in Rust instead of CPython. The
decision is the same, including `policy_id`, `reason`, and `attributed_to`; the
native path exists to lower per-call cost, not to change policy.

A policy is either fully native or fully Python. Four stateless detectors have a
Rust port and are native when used without parameters:
`ansi_escape_output_guard`, `crlf_header_injection_guard`,
`download_extension_guard`, and `code_eval_exec_guard`. Any other detector, a
detector with `with` parameters, a `modify`/`set` rule, an `on`/`when` form
outside the plain condition language, an overlay, a `disable` list, a shadow
rule, or a mesh ceiling makes the planner decline the whole policy, so the two
engines can never disagree about which rule applies. A failure during native
evaluation also falls back to the Python engine for that event. Policies below
eight rules (override with `INTERLOCK_NATIVE_MIN_RULES`) stay on the Python
engine because crossing the JSON boundary would cost more than the evaluation it
saves.

The default pack is intentionally not native-eligible: its parameterised
detectors and rewrites keep it on Python. To see what the fast path saves,
`scripts/bench_overhead.py` runs a native-eligible policy
(`benchmarks/overhead/native-policy.json`) through both engines on the same
corpus and reports the per-action speed-up beside the normal overhead gate.

The same engine has a C ABI (`il_eval_plan`, `il_abi_version`) in a separate
`rust/ffi` library for non-Python processes; `scripts/check_native_abi.sh`
builds it and runs an in-tree C caller. It is not needed for normal use.

## Safety of the evaluator

Policy files are data, and the evaluator treats them as untrusted:

- No `eval`, no imports, no attribute access. `arg` paths index dicts and lists
  only, so `"__class__"` is just a missing key.
- Detectors are looked up in the detector package by name. Nothing else can be
  imported.
- An exception while evaluating a rule blocks the call; it never allows it.
- One compiled policy is safe to evaluate from many threads.
